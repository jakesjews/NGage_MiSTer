## The observed loop is a kernel fault halt

ROM `cs0.bin`, based at `0x50000000`, contains `eafffffe` at `0x5031e394`:
`B 0x5031e394`. The code starting at `0x5031e340` copies the kernel fault
record from `0x40000418/1c/10` to device offsets `0x47f0/47f4/47f8`, writes
reset-request/reason values, calls `0x5031c2e0` to mask **both IRQ and FIQ**,
then branches to itself. This is not a WFI instruction or an idle loop.
A pending interrupt remaining masked there is the expected consequence
of entering the fault epilogue, not evidence of a WFI wake-up failure.

The existing 78 MHz board screenshot
`build/hardware/game/sonicn-v2d78/idle.png` in the main checkout decodes to
category **PLAT**, reason **0x1005b**. The same reason is documented in the
bring-up log for a system-critical thread panic; the reason alone does
not identify the originating defect. In particular it does not establish
an ARM architectural exception or a timing failure.

The source of reason `0x5b` is also visible in this ROM: at `5032d7c8`,
the thread exit routine checks exit type 2 and bit 2 of the thread flags
at offset `0x20`; `5032d800/804` raises the platform fault. The panic
reason and category arrive in `r2/r3`, before this terminal fault replaces
them with the general critical-thread reason. The retained ring and
memory dump are intended to recover those original arguments.
[Critical-thread path](arm9v2/s14/critical-panic-disassembly.txt).

## WFI and mask regression

`wfi_irq.S` covers masked IRQ arriving during WFI, IRQ already high before
WFI, an unmasked IRQ during WFI, and a new IRQ after a completed WFI while
repeatedly saving/restoring masks. It uses the exact EKA1 helpers at
`0x5031c2cc` and `0x5031c2f4`, including `MSR CPSR_fc`, with caches and MMU
on. Existing `rtl_misc` retains the uncached WFI and legacy-WFI coverage.
All nine configuration/latency runs pass without a core change.

The new `@@ qemu: irq` reference driver executes the same binary on QEMU
ARM926. The ordinary `none` machine has no timer, so its RAM also covers
BENCH and the driver observes the test's two ARM store encodings to apply
IRQ/IRQ-timer effects through qtest's CPU GPIO. Stores execute normally.
The timer counts stepped instructions rather than FPGA clocks; the test
compares final architectural results, not arrival PCs or elapsed counts.
WFI runs with `continue`, not single-step, and both delayed WFI cases must
actually block until the timer's IRQ is applied. QEMU's ti925t treats this
encoding as a NOP; it is deliberately not used as the WFI authority.
The ARM926 signature agrees with ZAP and both V2 predictor settings.

## Confirmed whole-core harness defect: truncated MMC host reads

The slot-0 HPS read adapter in **both** `coreboot_main.cpp` and
`top_main.cpp` unconditionally supplied 256 words (512 bytes). The card
now requests aligned eight-sector chunks for CMD18 (`sd_blk_cnt = 7`).
For example, a CMD18 starting at sector 33 asks HPS for sectors 32–39;
the old adapter delivered only sector 32, then dropped ACK. Sector 33
never became valid. Both the current V2 and fresh ZAP device logs contain
repeated MMC data timeouts (`0x80`) and subsequent command timeouts (`0x40`).
The standalone MMC bench already modeled burst lengths correctly, so its
passing results did not cover this whole-core adapter gap.

The fix exposes the existing slot-0 block count through the simulation
HPS stub and latches `(sd_blk_cnt + 1) * 256` with the accepted LBA. It
preserves the per-word delay, single-block timing and beyond-image zeros.
No CPU, cache, board-device RTL or generated netlist changes. This is a
**simulation fix**, not an explanation of the physical board's panic.

`make -C sim hps-read-test` (also run for the top adapter by `make top`)
uses `sim/harness/hps_read_test.sh` to compile a regression against either existing
whole-core generated model. It calls the actual host adapter without
clocking the RTL: 1, 2, 5, 8 and 32 sectors, changing the input descriptor
after acceptance, checking every buffer address/data word and ACK, including
zeros beyond the image. Both top/coreboot adapters pass with both CPU
configurations. Restoring the old single-sector limit fails the four
multi-sector cases. The requested 40-second comparison is being restarted
with this correction; old splash-only runs are not successful UI evidence.
