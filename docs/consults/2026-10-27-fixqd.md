# FixQD investigation, 2026-10-27

Current result: the historical utility is authentic, and the instrumented
copy is confirmed to apply its intended RAM changes on this firmware.
Same-RBF tests demonstrate no useful throughput improvement in either
Tony Hawk or Call of Duty. Occasional frame-pacing effects remain unmeasured.
The staged experiments below retain their original limitations and chronology.

The user's report links https://archive.org/details/fixqd. The original
release exists at https://sourceforge.net/projects/almalert/files/fixqd/0.666/
and is dated 2006-01-25. The Archive's 2,157-byte installer and the installer
inside the author's ZIP are byte-identical:
`757a31eede57d85bd372977c5afbf19a5779d34769770e8b0b34404c0e3b07fd`.

The original source was recovered from the author's SVN repository:
https://svn.code.sf.net/p/almalert/code/trunk/fixqd/src/FixQD.cpp
(export revision 403, file last changed in r282; initial import r168).
The only subsequent source log entry renames a notification callback.

## What the source establishes

The SIS installs a 2,728-byte startup recognizer, `FixQD.mdl`, under
`!:\system\Recogs`. Its worker waits for startup state 203, opens the shared
`*Sysap::$STK` chunk and loads `gd1eng.dll`. It finds the engine object and
its inactive callback by deriving addresses from DLL exports 1 and 4,
sets the object's word 19 to one, and substitutes the inactive callback
for another callback in that shared chunk. The helper then exits.
There is no CPU-clock change in this source. It is a RAM-state workaround,
not a rewritten ROM or an FPGA optimization.

For the firmware used here, GD1ENG export 1 is 0x510f089d, the located vtable
is 0x510f2bc0, and export 4 + 56 is 0x510f18b1. Inspection of that firmware
shows the inactive callback sets object offset 0x4c to one; a substantial
GD1ENG routine checks that flag at 0x510f13c4 and returns early when set.
This supports a real mechanism for suppressing engine work. It does not
measure its CPU share or establish the effect on game FPS or frame pacing.
The Symbian SDK's `apfrec.h` identifies `\System\Recogs\` as a recognizer
search path scanned on all drives, so an E: card is an intended load location.
Broad online claims about periodic scans/stutter are not substituted for
measurements of this core.

## Controlled hardware test

The existing FrameProfileV2 RBF is retained byte-for-byte at 104 MHz, with
its paired full-image counter reader. The unchanged baseline gives 6.533
changing complete uploads/s in CoD's initial forest and 18.125 in the
braked Tony Hawk Warehouse scene. Both use paired, stable counter snapshots.

Separate copies of the existing MMC images add only the author's unmodified
recognizer. All 790 original CoD files and all 30 original Tony Hawk files
are verified byte-identical, as are the partition tables, image lengths,
and trailing MMC identity sidecars. The original cards are not modified.
The existing C: save mount is retained without reset or copying. This is a
reversible diagnostic setup, not a proposed default distribution change.

Card hashes, extraction manifests, original source and package provenance
are under `build/timing-closure/research/fixqd/`. Hardware captures are under
`hardware/rfframev2fixqd104-{cod,thps}/` within the timing-closure directory.

Runtime patch application and performance effects are not yet confirmed.
A boot or a successful game launch alone does not prove that this silent
startup recognizer found and patched the target object.

The first unmodified-recognizer CoD test boots by 50 seconds and averages
6.500 changing complete uploads/s (30 paired samples, 6–7), versus 6.533
baseline. No incomplete/untracked uploads, sampled CPU faults or FPGA
flash-loader errors occur. This is no demonstrated gain, but application of the silent RAM patch
was not directly observed, so this run alone cannot rule out FixQD.

A separate diagnostic copy now appends 64 bytes to the MDL and branches to
one `User::InfoPrint` call only after both target matches and both RAM writes.
It displays `FixQD applied`. The target search, callback/flag values, imports,
exports and relocation payload are preserved; E32 offsets and additive code
checksum are updated. The injected Thumb code and ARM interworking pass an
isolated Unicorn check, including the flag write, descriptor text, preserved
registers/stack and return address. This is a test-only acknowledgement,
not the unmodified public utility and not a default core change. Runtime
confirmation is pending. Evidence: `acknowledgement-manifest.json`,
`acknowledgement-unit-result.json` and `hardware/rfframev2fixqdack104-*`.

The first acknowledgement capture started screenshots at 12 seconds and
showed the LCD test pattern through 56 seconds; the phone idle screen was
visible at 89 seconds with no sampled CPU-fault record. That run does not
establish normal boot time or plugin application. A follow-up diagnostic
moves only the acknowledgement 30 guest seconds later using `User::After`
in the detached helper thread, and waits until 50 seconds before capturing.
The follow-up phone is idle by that 50-second check. The cause of the first
capture's delayed visible startup is not isolated; do not attribute it to
FixQD or normal gameplay. The delayed injected code also passes the isolated
instruction/stack/interworking check.

No acknowledgement was visible in the delayed test's 50–89-second capture
window. This remains inconclusive. A further diagnostic places the added
code inside E32's declared executable-text region, moving the import address
table and rebasing its 40 literal references. All 80 original code relocations
are checked, the import/export values are preserved, and code checksum and
file offsets are updated. The isolated code test passes again. Earlier
variants placed the acknowledgement beyond the original text range; their
lack of a popup must not be treated as proof that FixQD itself failed.
The corrected-layout CoD test is idle by 50 seconds, but again shows no
acknowledgement in the 50–89-second capture window. It has no gameplay
measurement. None of these popup tests establishes whether the original
recognizer loaded or whether its RAM patch applied.

## Firmware-log follow-up

The existing `dbg_sti` block can capture the firmware's debug text into its
existing DDR3 ring, read over SSH with `tools/mister_trace.py fetch-sti`.
It is disabled along with the CPU/data trace rings in the current profiling
build. A separate `tlb-fix-rfframestiprof104-s13` variant enables only this
existing text logger. All CPU sources, generated CPU, framework files,
clock settings and constraints are byte-identical to FrameProfileV2.
Whole-core lint with and without the debug macro, and standalone logger
lint, pass. The fit completes with 35,201 ALMs, 41,873 registers, 484 M10Ks and
42 DSPs; minimum setup is -2.195 ns and hold +0.113 ns. It remains a
diagnostic with failing setup, not a release build. Its RBF SHA-256 is
`cba8a36e9f3ecaf9a2faccfb2cf9e9b359465347aa0f52608d5a6248c04704cd`.
The first hardware boot with the logging recognizer is running. The purpose is positive evidence of recognizer loading
and patch application, not an assumed performance fix.

The original MiSTer INI and core configuration are restored with matching
SHA-256 hashes, along with the best stripped 104 MHz build and original
Tony Hawk card. The phone is idle at the 50-second check; the temporary
input server has exited. Evidence is under
`hardware/fixqd-restored-stripped104/`. The separate diagnostic cards remain
available for the logging follow-up. The restored build's known setup
slack remains -1.301 ns; restoration does not establish timing closure.

A follow-up diagnostic recognizer uses four `RDebug::Print` markers:
recognizer entry, PatchL entry, successful patch, and worker exit/error.
The SDK import library identifies EUser ordinal 836, and the loaded ROM's
export table resolves it to 0x503af1ac. Only short branches and added text
are inserted; the original search and patch remain. Four isolated Unicorn
comparisons verify each hook against the displaced original instructions,
including live stack and register state while the mock logger clobbers
caller-saved registers. E32 import addresses, offsets and code checksum
are rebuilt. This is test instrumentation, not a proposed firmware change.
The separate CoD image retains all 790 original files byte-for-byte.
Evidence: `research/fixqd/log-probe-{manifest,unit-result}.json` and
`research/fixqd/log-card-manifest.json` under the timing-closure directory.
Hardware application remains unverified; the first STI capture is pending.

## Positive runtime confirmation

The STI build reaches phone idle by 50 seconds, captures 3,501 firmware-log
bytes and reports zero dropped writes. The log contains, in order,
`FIXQD: recognizer entered`, `FIXQD: PatchL entered`, `FIXQD: applied`, and
`FIXQD: worker exit 0`. The applied marker is reached only after both target
matches and both original RAM writes. This confirms application of the
logging copy on this firmware/card path; the earlier popup absence was
not reliable evidence of failure. CPU-fault and FPGA flash-loader-error
observations are zero. A paired CoD measurement and same-RBF unpatched
control are now running. Evidence: `hardware/rfframestiprof104-fixqd-cod/`.

The confirmed-patch CoD window averages 6.800 complete uploads/s; the
same-RBF unpatched control averages 6.833 (30 paired samples each).
Both have zero incomplete/untracked uploads and no sampled CPU-fault or
FPGA flash-loader-error records. The unpatched boot log has no FixQD
markers. Changing-picture rates are 0.633 and 1.100/s: this stationary
scene repeats images as its small background animation settles. This is
not evidence of a rendering-throughput regression, nor are the earlier
6.5 changing-image counts interchangeable with these animation states.
The full-upload comparison shows no useful throughput gain from FixQD in
this CoD scene. It does not rule out rarer frame-pacing effects. Tony Hawk
is the next same-build control. Evidence: the two
`hardware/rfframestiprof104-{fixqd,control}-cod/mission-*-summary.json` files.

Tony Hawk's repeat boot is idle by 50 seconds. A stable full-ring capture at
80 seconds positively contains all four FixQD markers before game launch.
The braked Warehouse scene averages 18.083 changing complete uploads/s with
the patch versus 18.333 without it on the same STI RBF (24 paired samples
each). Instructions/s are 45.381 M versus 45.800 M. Both have zero incomplete
or untracked uploads, sampled CPU faults and FPGA flash-loader errors.
Screenshots confirm the same stopped starting view; this is not deterministic
replay. There is no useful throughput gain. Rare hitching remains outside
this short-window measurement. Evidence: `hardware/rfframestiprof104-fixqd-thps-recheck/`
and `hardware/rfframestiprof104-control-thps/` under timing-closure.

The earlier Tony Hawk logging run is not the confirmation run: its initial
capture contained only recognizer entry. The firmware ring was subsequently
overwritten by normal traffic, so the absence of later markers in that late
capture cannot establish a failed patch. `fetch_sti_fast.py` now reads the
whole DDR ring twice in one SSH session and requires matching pointers and
bytes. Its pointer's wrap bit is not saturated; long-running captures must
not be represented as complete boot histories.

## Independent NOS logging experiment

The project's own `model/nos-stub/nos_isi.c` formats every ordinary incoming
and outgoing ISI message and calls guest `Kern::Printf`. FPGA debug capture
being disabled does not remove these software calls. Tony Hawk generates
enough traffic to overwrite the firmware ring. This identifies avoidable
work, not yet its performance cost.

The original stand-in rebuilds byte-identically. A diagnostic copy replaces
only its two ordinary traffic `log_text` calls (ARM VAs 0x514a2a94 and
0x514a2e54) with NOPs. Error logging and all protocol handling remain intact.
Separate flat firmware images are generated from the original Phoenix pair;
their only differences are those instruction words and the required integrity
digest. CS1 is byte-identical, and the baseline matches every current FPGA
patch-ROM record. The same STI RBF, original game cards and existing C: save
are used. No Nokia code or framework source is changed. This is an isolated
test of project-owned logging, not a proposed binary-patching distribution.
Provenance is in `research/nos-traffic/manifest.json` under timing-closure.

Both flat-image variants reach phone idle by 50 seconds. Firmware captures
confirm ordinary NOS traffic in the control and its absence in the quiet
variant. Tony Hawk's same stopped scene gives 18.083 versus 18.500 changing
complete uploads/s, 45.356 versus 45.902 M instructions/s (24 paired samples
each). This is a small single-window difference, not the requested five-FPS
gain or a repeatability result. Both variants still have STI capture enabled;
removing software prints also removes their capture writes, so this does not
isolate guest instruction cost or establish the effect in a stripped build.

Quiet CoD gives 6.800 complete uploads/s and 6.733 changing complete uploads/s
over 30 paired samples, 54.865 M instructions/s. Its comparator is the earlier
same-RBF Phoenix control at 6.833 complete uploads/s, not a newly measured
flat-image control. There is no useful demonstrated gain. Both games have
zero incomplete/untracked uploads and no sampled CPU fault or FPGA
flash-loader error. This diagnostic is not promoted; no stand-in source or
distributed binary is changed. Evidence: `hardware/nos-traffic-{base,quiet}-thps/`
and `hardware/nos-traffic-quiet-cod/` under timing-closure.
