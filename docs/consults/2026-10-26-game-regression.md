## First successful JTAG acquisition

`hardware/jtag-fault1/capture.stp`, decoded CSV and `annotated.txt` contain the actual CPU sequence. The fast-fit 78 MHz probe build captured it (worst setup -0.369 ns); the full-effort identical probe build subsequently passed all 16 setup/hold/recovery/removal checks, minimum setup +0.201 ns and hold +0.092 ns. A repeat capture on that timing-clean diagnostic is underway.

- The kernel calls ROM Mem::Copy from 0x5033c1b8 with destination 0xfff00000, source 0x8040938c and length 0xf84 while loading Asphalt.
- The backwards copy first stores eight words at 0xfff00f64. It raises a data abort at 0x503a247c, with pre-abort CPSR 0x2000001b (UND privileged mode).
- The exception handler reads CP15 c6 and c5: **FAR 0xfff00f64; FSR 0x05**. Thus this is a section translation fault, not a meaning inferred from the final 0x10000000 generic kernel fault reason.
- Saved R0=fff00f84, R1=8040a2f0, R2=00000f84, LR=5033c1bc. R3-R10 contain the expected game code words, beginning e5843020. The data-port acknowledgement probe can show victim data during a cache miss; the saved architectural registers demonstrate that the load itself returned the correct words.
- The first trigger position retained only 256 samples before the kernel record. The repeat uses 1792 pre-trigger samples to inspect the preceding loader operations.

Rizin and the existing ARM disassembly helper are being used to follow the captured ROM control flow. The MMC's E32 executable was extracted locally for matching code words; no ROM patch or gameplay workaround has been added.

The second capture (`jtag-fault2`) reproduces the exact same FAR/FSR and faulting instruction on the timing-clean full-effort probe build. The longer history identifies medmmc.pdd calling the kernel descriptor-copy routine: the destination comes from a descriptor at 0x80803480 whose pointer word at 0x80803488 is 0xfff00000. The next runtime trigger watches the write of that pointer, to trace its origin before adding more probes.

The fourth capture (`jtag-fault4`) changes the pointer interpretation: the kernel is intentionally mapping that region. It updates the page directory at VA 0x41003ffc with descriptor 0x0a2bc031, drains the write buffer, and returns 0xfff00000 as both code load and run address. The apparent bad pointer is therefore not enough to blame the loader. The immediate section fault later is consistent with a stale invalid translation, which the next probe must verify.

An independent focused architectural test now reproduces invalid-descriptor caching: fault on unmapped 0xfff00100, install a valid section descriptor and drain writes, retry without a TLB flush. Committed CPU fails check 5 (unexpected second abort); QEMU ti925t passes. ARM DDI0100I B4.5.1, page B4-16 explicitly requires translation-fault table fetches not to update the TLB. Earlier repository notes describing cached translation-fault entries as ordinary ARM behavior are incorrect. Source: https://e2e.ti.com/cfs-file/__key/communityserver-discussions-components-files/1023/ARM-Architecture.pdf#page=716

The candidate correction and reproducer are isolated under `build/timing-closure/tlb-fix-experiment/` and `tlb-fault-retry/`; committed CPU RTL remains unchanged pending validation. Two diagnostic builds add a D-TLB walk/address/descriptor probe (`mmu-jtag78-s2`, `mmu-jtag78-fast-s2`) while preserving all functional behavior.
