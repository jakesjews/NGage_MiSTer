# ARM9V2 session 1: merged baseline, design and fetch-cycle predictor

**Stopping point:** master merged into `codex/arm9`, then `codex/arm9v2`
created; the eight-stage design is documented; F1/F2, a 256-entry BTB,
eight-entry return stack and raw instruction queue are implemented and tested
as a standalone component against the actual short-read I-cache. **D1 through
W are not implemented.** `CORE="ARM9"` still runs the paused core and ZAP
remains the default. There is no V2 whole-program cycle count, integrated CPU
fit, whole-device build or board measurement yet.

The same front-end RTL at seeds 2/3/4 has worst slow-corner slack
**-0.574 / -0.856 / -0.895 ns**, median **-0.856 ns**, at 104 MHz, with
**1,090 / 1,084 / 1,085 ALMs**, two M10Ks and positive hold slack. This is
component evidence; it does not satisfy the complete CPU gate. The 47 M/s
gameplay goal remains unmeasured.

The merge keeps `ICACHE_PREFETCH`, `DCACHE_SIZE`, the D-cache debug outputs,
the newer bench taps, and both existing cores. Necessary short-read
compatibility resolutions were:

- The cache's live lookup and its saved victim may use different ways. A
  short-read store hit selects the registered live way; a fill uses the FSM's
  saved way. The short-read write/forward qualification uses the same live
  lookup decision. These are merge adaptations in `zap_dcache.sv`, not a new
  store-miss or write-back mechanism. **No `zap_dcache*.sv` changes were made
  after the merge.** The other thread owns those mechanisms.
- The short tag path captures the immediate compare for hit-under-miss
  bookkeeping; the long ZAP path retains its existing compare alignment.
  The first merged attempt exposed this alignment assertion and was corrected
  before the merge commit.
- Master's BTB supplies its decision earlier than the paused fetch expected.
  An F1-to-F2 decision/target register restores the paused metadata alignment
  while keeping master's registered lookup. The old cycle windows stay exact.
- Bench hierarchy probes distinguish the two cores and their short/long cache
  lookup stages. Generated Verilog was regenerated from the resolved sources.

Baseline ZAP at 0:0 is exactly the requested **cache 789,362, ctrand1 72,413,
crand1 72,922**. Existing binaries and QEMU results were used, with missing
artifacts copied from their already-built sibling worktrees. No old binaries
or references were rebuilt or rerun. No firmware boot bench was run, no `sys/`
file changed, and no branch was pushed.

## Implemented front end

The independent GPL implementation lives in `rtl/cpu/arm9v2/`. The Pocket
design documentation was read for ideas only; no unlicensed RTL was copied.

`arm9v2_predict` stores a coherent 60-bit entry: full source tag, source
instruction state, target/state, two-bit counter and branch kind. Its 256
entries occupy 15,360 bits in two M10Ks. Entry RAM and source-PC metadata
capture on the same edge. During F1, tag/counter/RAS selection chooses the
next launch; there is no additional prediction-decision stage. In a trained
three-target loop, each successive queued word is a predicted target and
arrives on the next clock, with no lost slot.

Valid state is cleared separately from the RAM contents. Same-edge feedback
and lookup see the new coherent entry. Saturating-counter feedback is a
registered backend record supplied through the component interface. A miss
starts weakly not taken and the first taken feedback makes it weakly taken.
Full tags and Thumb state prevent index aliases from becoming valid hits.

The eight-entry RAS saturates its depth and wraps its pointer. A recognized
predicted call pushes the sequential link including instruction state; a
return pops only if nonempty. Underflow uses the checked BTB target. Packets
carry the pointer/depth before speculation; repair restores those and applies
the actual call/return, or clears the stack. Contents are prediction-only and
are not architecturally rolled back. Decode recognition of BX lr, POP/LDM pc
and MOV pc,lr, and actual prediction validation, are **future backend work**.

`arm9v2_fetch` aligns F1/F2 PC/state/epoch and prediction records to the existing
short-read cache ports. Eight register entries hold raw word, PC, state,
fault/pending and prediction metadata. There is no Thumb expander here and
no queue-empty bypass into D. Cache hit/permission logic cannot select the
instruction payload or reach decode operands: ACK/fault/retry govern queue
insertion and status. Queue full or an unacknowledged lookup holds the lookup
metadata and RAM enable together. The queued head is independently consumable
unless its fill is pending.

An explicit `HOLD_READ=1` option in `zap_ram_simple_nopipe` retains both the
write-first collision flag and its data during disabled read clocks. Without
this, the first held clock after a same-edge write/read reverts to the stale
RAM output. The new predictor selects this option; existing callers keep the
default behavior. This is the only shared RTL change after the merge.

### Cases covered and remaining contracts

| Case | Implemented handling and evidence |
|---|---|
| Sequential hit stream | F1/F2 and raw queue sustain one word/clock; real cache verifies word/PC alignment. |
| Correct trained direct prediction | Target is the next F1 lookup; older F2 is retained. Unit and real-cache loops assert consecutive-clock delivery. |
| Counter changes / index aliases / ARM versus Thumb | Directed counter sweep, all 256 indices, high address aliases and state mismatches. |
| Predictor read/write collision, then hold | Coherent write-first record retained for five disabled clocks and across a later same-index replacement; tested in SV and generated Verilog. |
| Predictor clear with held output or feedback | Valid state and RAS clear have priority. Already-issued prediction metadata still requires backend validation. |
| RAS wrap, underflow, repair | Bounded depth, newest-first returns, fall back when empty, actual call/return after restore, Thumb links. Speculative overwritten contents may cause a later prediction miss. |
| Queue full / decode holds | Stop lookup advance without overwriting a queue entry; deterministic varied holds preserve ordering. Full-to-pop recovery may have a local admission bubble. |
| Local cache retry | Keep older queued instructions, cancel/relaunch F2 and younger F1, restore the F2 RAS checkpoint. |
| Backend redirect during a held lookup | Kill the old epoch, keep the untagged request address until it drains, then start the newest redirect. Repeated redirects wrap the epoch safely while old queue entries remain inaccessible. |
| Early instruction return / late fill fault | Mark queued records pending, prevent consumption, and attach final fill fault before release. Synthetic delayed-fault checks cover this; real-cache bench covers successful fills and translated faults. |
| MMU-off fetch | Real generated cache exercises its uncached response path. |
| Thumb | Unit bench checks halfword PC/state metadata. Expansion and real-cache Thumb instruction execution await D1. |
| Backend fault priority, IRQ/FIQ, stale prediction, load-PC and exception return | Interfaces exist but execution and precise architectural ordering are not implemented; current component tests cannot prove them. |

The backend must supply registered redirect/update records. It must suppress
younger side effects until older memory faults and predicted PC writes are
resolved. It owns ARM/Thumb target alignment and return classification. A
predictor miss or corrupted speculative stack must only change fetch timing,
never an architectural result. These remain explicit integration contracts.

## Front-end fit and area

Only `TRIAL=arm9v2_frontend` was built in this session, on `ubuntu` with
`sim/cpu/quartus/run.sh`. It includes real F1/F2, BTB, RAS and queue with
registered stimulus and registered outputs, **not caches or D1 through W**.
Ten 32-bit stimulus shift registers are declared; unused bits are removed by
synthesis. The normal 5CSEBA6U23I7, 104 MHz/9.615 ns constraints and optimization
settings are used. No internal false paths or multicycle paths were added.

limit, and failed before placement. Folding observable metadata into three

## Risks and next session

The front-end BTB loop already consumes most of the clock budget. Cache RAM
placement, its permission/hold path, decoder backpressure and the complete
clock tree are absent from this fit. Preserve the raw queue boundary and do
not feed A/M admission or commit into the F1 target selection. Three seeds
quantify component variation but cannot predict the complete CPU placement.

RAS contents repair is deliberately approximate; backend target validation
and precise retirement are essential before it is safe to execute predictions.
Real-cache simultaneous bus error/late-fault cases, cache maintenance while
fetching, Thumb execution, flags, banked registers, LDM abort restoration and
background D-cache returns still need integrated tests. Component checks are
not an instruction-by-instruction equivalence result for V2.

**Resume with D1/D2**, using this queue interface and exactly one existing
Thumb expander. Register physical tags, class, PC-relative target/match and
LDM count/scan/8-bit offsets in D1; D2 reads the register file and stalls loads
there. Then implement the common three-registered-producer S/A network,
single rotator and multiplier, followed by M/W's registered memory address,
three-clock late load pickup and precise exceptions. Do not route the old
combinational ALU address into the D-TLB as an integration shortcut.

The old 85 windows are preserved as compatibility checks, not a V2 cycle
specification. New integrated windows must prove the stated zero-slot correct
prediction and three-clock load-use schedule and measure every redirect class.
Retain all tests, including `dhum_rtl`, for V2's final architectural gate.

The full eight-stage structural pass, its cycle reduction targets and its CPU
timing gate are **unfinished**. This session ends at the independently tested
front-end milestone. The whole-device compile remains gated on a complete CPU
fit. Once the complete CPU exists, measure seeds 2–4; if a structural pass
is still worse than -2 ns, stop and report its remaining chains. Only a CPU
median within 1 ns permits the specified whole-core integration build; board
104 MHz closure and 47 M/s gameplay remain the final acceptance result.
